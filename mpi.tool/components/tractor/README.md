# tractor - Trace Collector Runtime

Part of peat.

## What it does

A low-intrusion, `LD_PRELOAD`-based shared library that intercepts MPI (and optionally OpenMP/OMPT, OpenACC, GPU, and the transport APIs PSM2/PSM3/verbs/UCX/OFI) calls and records them into the trace files consumed by `mat`, `ctt`, `urpu`, `pet` and `qTV`. Also drives the PTP Daemon (PTPD) used to synchronise timings across nodes. Supports Intel MPI, MPICH, MVAPICH and Open MPI on Linux.

See [doc/README.md](doc/README.md) for older build/usage/trace-format documentation (note: marked outdated there, kept for reference).

- `src/t_signals.cpp`/`.h` - signal handling for clean trace flushing on crash/termination.
- `src/elf_parser.cpp`/`.h` - ELF/debug-info symbol resolution for call-site addresses.

- `src/transport_func_layers.pl`, `src/funcids_convert.pl`(`.old`) - code generators for transport-API functions and MPI function-ID tables.

## Transport-API profiling

Besides MPI/OpenMP/GPU calls, tractor can record events for the transport layer underneath MPI: PSM2, PSM3, UCX and OFI (libfabric), plus, for the patched mvapich2 build, native Verbs (`ibv_*`) and shared-memory (SMPI) channel calls. All layers share the same event/statistics engine (`src/t_transport.cpp`/`.h`, trace output in `*.transport` files) and are code-generated by `src/mpi_layer.pl` from the `CLASS_PSM2`/`CLASS_PSM3`/`CLASS_UCX`/`CLASS_OFI`/`CLASS_VERBS`/`CLASS_SMPI` function entries in `../common/mpi_func.inc`.

- PSM2/PSM3/UCX/OFI calls are intercepted via `dlsym(RTLD_NEXT, ...)`, so they work with any unpatched MPI, provided the process actually calls into the corresponding vendor library.
- Verbs fast-path calls (`ibv_post_send`, `ibv_poll_cq`, ...) are static-inline in `<infiniband/verbs.h>` and can't be `dlsym`-intercepted; they (and SMPI shared-memory calls) are only recorded when built against the patched mvapich2 sources that call `mv2_proxy_ibv_*`/`smpi_*` directly (`TARGET=mvapich2`).
- Hot polling loops (`psm2_mq_ipeek*`, `ibv_poll_cq`, `fi_cq_read`) coalesce consecutive no-op polls into a single event (`num_calls`/`total_clocks_bitween_calls`) instead of one event per call, keeping intrusiveness low.

There are two ways to get transport-API support built:
- `TRANSPORT=on` - compiles transport-API support into the main `libtractor*.so`. Only `TARGET=mvapich2` combines more than one layer this way: verbs (patched `mv2_proxy_ibv_*`/`smpi_*` calls) and psm2 (`dlsym`-intercepted) are compiled into the same binary (`src/Makefile`, `TARGET=mvapich2` block: `transport_func_layers+=-l verbs -l smpi -l psm2`), for a mvapich2 build that could in principle run over either its ib-verbs or its opa-psm2 channel. The other single-layer `TRANSPORT=PSM2/PSM3/VERBS/UCX/OFI` `Makefile` blocks are legacy/kept for reference and aren't used by the current `Build*.sh` scripts.
- `TARGET=transport_layers` - builds standalone per-layer shim libraries `libtractor_transport_{psm2,psm3,ucx,ofi}<suffix>.so` (installed under `../../lib/<compiler>/`), meant to be added to `LD_PRELOAD` alongside the main library for generic (unpatched) MPI builds. Each shim only ever contains one layer's functions.

Runtime switch (only meaningful when built with transport-API support):
export PEAT_TRACTOR_COLLECT_TRANSPORT=1  - enable transport-API event collection (default: off)

Note: `PEAT_TRACTOR_TRANSPORT_LAYER` is currently non-functional - the env-var parsing in `src/tractor.cpp`, the `t_transport_layer` enum/struct member in `src/tractor.h`, and the runtime `gt_info(transport_layer)!=...` check that `src/mpi_layer.pl`'s `make_class_transport` would generate are all commented out. In practice this means a `TARGET=mvapich2 TRANSPORT=on` build records events for whichever of verbs/psm2 the process actually calls into (nothing is filtered by layer at runtime), and there is currently no way to select a layer for it.

## llama.cpp pipeline profiling

Part of the base build, like OMPT, when it can be built: `LLAMA_PARSE=auto` (default; CMake `-DLLAMA=AUTO`) builds it when llama.cpp's headers are found - `LLAMA_ROOT=<llama.cpp source tree or install prefix>` (default: the `contrib/llama.cpp` submodule when it is checked out), else the installed ones (`pkg-config llama`, `/usr/local/include`, `/usr/include`) - and have the API of the wrappers (checked by `src/t_llama_probe.cpp`: a llama.cpp with another API is left out); `LLAMA_PARSE=on|off` (CMake `-DLLAMA=ON|OFF`) forces it. It adds wrappers for the coarse llama.cpp stages, the `CLASS_LLAMA` entries of `../common/mpi_func.inc` (no change of the library name): `llama_model_load_from_file`, `llama_init_from_model`, `llama_tokenize`, `llama_process`, `llama_get_logits_ith`, `llama_sampler_sample`, `llama_token_to_piece`, `llama_free`, `llama_model_free` and the scheduler calls libllama makes into libggml-base, `ggml_backend_sched_alloc_graph`, `ggml_backend_sched_graph_compute_async`, `ggml_backend_sched_synchronize` (the same for every ggml backend; with a GPU backend the device time shows up in `synchronize`).

- They are found with `dlsym(RTLD_NEXT, ...)`, so llama.cpp has to be built with shared libraries (`-DBUILD_SHARED_LIBS=ON`), and compiled against the `llama.h` found (two of them take structures by value): use the headers of the llama.cpp the traced llama.cpp was built from.
- Records are nested (`llama_process` -> `ggml_backend_sched_graph_compute_async`, ...), carry no parameters and are read as local events by mat/ctt/pet/qTV. Generated from `pinc/llama.code.inc`.
- `LLAMA_DEPRECATED=on` (CMake `-DLLAMA_DEPRECATED=ON`) adds `llama_decode`/`llama_encode`, deprecated in llama.cpp in favour of `llama_process`; they are under `#ifdef _PARSE_LLAMA_DEPRECATED_` in `mpi_func.inc`.
- A llama.cpp process does not need MPI: the trace is written at exit when it recorded any llama.cpp stage.
- The second remark of the com file lists the modules built into the library and, for the ones with a run-time switch, whether they recorded, e.g. `0:Modules: MPI 3.1(.openmpi5.gpu) OpenCL LevelZero OpenACC CUDA 13.5/CUPTI 130500(recording off) llama.cpp(stages on, ggml CPU kernels on) PTPD timer=nano`. CUDA says `recording failed` when `PEAT_TRACTOR_PARSE_CUDA=1` but CUPTI did not start (reported on stderr once, e.g. no driver); the run goes on without CUDA records.

### ggml CPU kernels

The same builds also wrap the ggml CPU backend (`CLASS_GGML_CPU`, generated from the declarations in llama.cpp's `ggml/src/ggml-cpu/*.h`): `ggml_graph_compute` (once per graph), every `ggml_compute_forward_<op>` kernel, `ggml_cpu_extra_compute_forward` (the extra buffer types' own kernels - repacked Q4_0/Q4_K/IQ4_NL weights (`CPU_REPACK`), AMX, ...: their matmuls never call `ggml_compute_forward_mul_mat`) and `ggml_barrier` between nodes.

- Off unless `PEAT_TRACTOR_PARSE_GGML_CPU=1`: every worker thread records its share of every node (some thousands of records per generated token). Measured on an 8-core desktop: about 5% slower generation; the default (pipeline stages only) is within noise.
- With it on, `PEAT_TRACTOR_MAX_THREADS` defaults to the number of CPUs + 8 and `PEAT_TRACTOR_MAX_NESTING_LEVELS` to 8 (the main thread nests `llama_process` > `ggml_backend_sched_graph_compute_async` > `ggml_graph_compute` > kernel > `ggml_barrier`); explicit settings are kept. Too low limits abort the run.
- Calls inside libggml-cpu are only intercepted when they go through the PLT: GCC's default for `-fPIC` code. Check a build with `objdump -d libggml-cpu.so | grep 'call.*ggml_compute_forward_rope@plt'`; clang and icx call (or inline) them directly unless built with `-fsemantic-interposition`.
- `ggml_cpu_extra_compute_forward` is tried first for every node: a short record when the node is not one of an extra buffer type.

## CUDA profiling (CUPTI) and cuBLAS

CUDA is one of the GPU APIs: `PARSE_GPU=on` (CMake `-DGPU=ON`) builds it when a CUDA toolkit is found (`CUPTI_PARSE=auto`), `CUPTI_PARSE=on|off [CUDA_ROOT=<CUDA toolkit>]` (CMake: `-DCUPTI=ON|OFF|AUTO [-DCUDA_ROOT=...]`, which also selects `PEAT_TIMER=nano`) sets it explicitly, also without `PARSE_GPU`. It adds `src/t_cupti.cpp` and the `CLASS_CUDA`/`CLASS_CUBLAS` entries of `../common/mpi_func.inc` (a GPU build: `.gpu` in the library name, once, as with OpenCL, Level Zero, OpenACC; linked to that toolkit's `libcupti`: use the CUDA version the application runs with). Recording is off unless `PEAT_TRACTOR_PARSE_CUDA=1`. Independent of `LLAMA_PARSE`, works for any CUDA application.

- Compilers: only host CUDA headers are compiled (`cupti.h`, `cublas_v2.h`, `cublasLt.h`), so it is not tied to a compiler or to nvcc. Checked with g++ 16, clang 23, nvc++ 26.9 (`TARGET=openmpi`; `openmpi5` adds `-fms-extensions`, which nvc++ rejects) and icpx 2026.1 (`COMPILER=intel`, Intel MPI, Makefile and CMake: `libtractor.impi.gpu.so` with llama.cpp tracing and CUDA), CUDA 12.0 (CUPTI API 18, Debian/Ubuntu packages), 12.9 and 13.5: the activity records are read through layouts every CUPTI from CUDA 11.8 on has (`Kernel9`, `Memset4`, and `Memcpy5`/`Synchronization`/`GraphTrace`, whose newer versions only add fields at the end). `auto` decides with a probe compiled by the MPI wrapper with the compiler's own options, so a compiler or a machine that cannot build it just builds without it (without the CUDA layer then; `PARSE_GPU=on` with no GPU API found at all gives the usual warning); `on` stops with what was missing.
- Toolkit: `CUDA_ROOT`, else `NVHPC_CUDA_HOME` (set by env.sh for `compiler=nvc:<cuda version>`), `CUDA_HOME`, `CUDA_PATH`, `/opt/cuda`, `/usr/local/cuda`, `/usr`. CUPTI is found in all three layouts: `extras/CUPTI/{include,lib64}` (NVIDIA installers, NVHPC), `targets/x86_64-linux/{include,lib}` (e.g. Arch's `cuda`) and `include`, `lib/<multiarch>` (Debian/Ubuntu `nvidia-cuda-dev` + `libcupti-dev`, found as `/usr`; system directories are not added to `-I`/`-L`/rpath). The library is tied to that toolkit's `libcupti.so.<major>`: with several CUDA versions installed, set `CUDA_ROOT` to the one the application is built with (a CUDA 12 application, e.g. for pre-Turing GPUs, is not traced by a library built against `/opt/cuda` = CUDA 13).
- Build scripts: `src/Makefile` and `src/CMakeLists.txt` read `LLAMA_PARSE`, `LLAMA_ROOT`, `LLAMA_DEPRECATED`, `CUPTI_PARSE` and `CUDA_ROOT` from the environment themselves (CMake: where the `-D` option is not given; a `LLAMA_ROOT` from the environment alone makes it `-DLLAMA=ON`), so `Build.sh` and `Build-cmake.sh` pass nothing. In the `BuildAll*.sh` builds llama.cpp tracing is there whenever its headers are found, and the GPU builds (`PARSE_GPU=on`) get CUDA when a toolkit is found.

- GPU activity (CUPTI activity API): every kernel, copy (`cuda_memcpy_htod`/`dtoh`/`dtod`/`ptop`/`htoh`), `cuda_memset` and synchronization (`cuda_sync_context`/`stream`/`event`/`stream_wait_event`), as top-level records on a thread lane of its own per CUDA context and stream. CUPTI takes its timestamps from tractor's clock, so they are on the host time line. A kernel record is written with the kernel's own name - demangled, without return type and parameter list, `::` as `.` (`:` separates the fields), e.g. `mul_mat_vec_q<(ggml_type)2, 1, false, false, false>` - instead of `cuda_kernel`; the tools give a name they do not know an id of its own (`Func_ID::add_by_name()`), so the kernels are reported one by one. `PEAT_TRACTOR_CUDA_GRAPH_TRACE=1` records whole CUDA graphs (`cuda_graph`) instead of their kernels.
- Host CUDA runtime calls (CUPTI callback API): `cudaLaunchKernel`, `cudaMemcpyAsync`, `cudaStreamSynchronize`, ... (the `cuda*` entries of `mpi_func.inc`), nested where they are made (`llama_process` > `ggml_backend_sched_graph_compute_async` > `cudaLaunchKernel`). No call site address: from a CUPTI callback only libcupti's frames are at hand.
- cuBLAS: `dlsym` wrappers of the compute calls ggml-cuda makes (`cublasGemmEx`, `cublasGemmBatchedEx`, `cublasGemmStridedBatchedEx`, `cublasSgemm_v2`, `cublasSgemmBatched`, `cublasSgemmStridedBatched`, `cublasStrsmBatched`, `cublasLtMatmul`); their GPU kernels are recorded by CUPTI under cuBLAS's names (e.g. `maxwell_sgemm_128x64_tn`).
- Record layout: every CUDA and cuBLAS record has the class dependent part of the GPU class (`:num_arguments:num_out_arguments:num_extra_arguments`, see doc/Tractor.Trace.Format.Description.pdf), its arguments (hex) are:

  | record | arguments |
  |---|---|
  | host CUDA call (`cuda*`) | correlation |
  | kernel (written by its name) | correlation, stream, grid x, y, z, block x, y, z, shared memory bytes |
  | `cuda_memcpy_*`, `cuda_memset` | correlation, stream, bytes |
  | `cuda_sync_*` | correlation, stream (`ffffffff`: device wide) |
  | `cuda_graph` | correlation, stream, graph id |
  | cuBLAS call | none |

  The correlation id is CUPTI's: a GPU record and the host call that caused it (`cudaLaunchKernel`, `cudaMemcpyAsync`, ...) have the same one. mat pairs them (`GPU::parse_cuda()`): one `PEAT_RT_Bind_Completion` line per pair in the bind file (call -> GPU record), and the time from the start of the call to the end of the GPU work in its GPU statistics (transfers keyed by bytes, executions by stream). qTV draws the pairs as GPU execution (launches, `cudaGraphLaunch`), GPU transfer (`cudaMemcpy*Async`, `cudaMemset*`) or completion (synchronizations) messages. The readers take every record of the CUDA group and every function they only know by the name in the record (`peat_is_cuda_func_id()` in `common/mpi_func_ids.h`) as a GPU class one.
- With it on, `PEAT_TRACTOR_MAX_THREADS` defaults to the number of CPUs + 24 (stream lanes) and `PEAT_TRACTOR_MAX_NESTING_LEVELS` to 8; explicit settings are kept.
- The GPU records still buffered by CUPTI are flushed from an exit handler registered at the first CUDA call (it runs before the CUDA runtime's own ones) and again before the trace is written.
- Measured on a GTX 1080 with llama.cpp (1B model, every layer on the GPU): about 5-10% slower generation, 68k kernels per 128 tokens.

## Processes without MPI rank

A process not started by an MPI launcher (no `PMI_RANK`/`OMPI_COMM_WORLD_RANK`, e.g. a llama.cpp application) is written as rank 0 of a one-rank, one-node run, under the per-process template `<PEAT_TRACTOR_FILE>_<pid>`: `tractor_t_<pid>.app.gz`, `tractor_t_<pid>.{mpi,hwc,com}.0.gz`. The node records of the `.app` file (host, frequencies, sync points) are filled from the process itself, so ctt/mat/qTV read it as any other trace: `ctt -i tractor_t_<pid>`. (The pid is joined with `_`, not `.`: the tools take the rank from the first dot-separated part of a file name that starts with a digit.)

Runtime switch: export PEAT_TRACTOR_PARSE_LLAMA=0 - do not record llama.cpp stages (default 1, builds with llama.cpp only)
